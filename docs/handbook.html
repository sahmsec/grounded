Operator handbook

Everything needed to run, feed and repair the course assistant — written for whoever is on the other end of "it stopped working", including you in three months.

What it is, in one rule

The assistant answers only from the course material you give it, shows the passage each answer came from, and refuses when the material does not cover the question.

That refusal is decided in code, before any model is contacted — a similarity score below the gate ends the request. It is not an instruction in a prompt that the model might ignore. Every change you make should preserve that property; it is the whole reason to run this instead of a general chatbot.

Three things happen for a typical question:

  1. The question is turned into a vector and matched against stored passages.
  2. The best score is compared with the gate. Below it, the fixed refusal is returned and no model runs.
  3. Above it, the surviving passages and the question go to the model, which must cite what it used.

Greetings, thanks and questions about the assistant itself are answered in code without any model call. Follow-ups like "explain more" are rewritten into standalone questions first, because "more" means nothing to a search index on its own.

Running it

# first time only
npm install
npm run db:up          # Postgres + pgvector in Docker, port 5433
npm run migrate
npm run seed

# every day
npm run db:up          # if Docker was restarted
npm start              # http://localhost:3000

Two pages: the chat at / and the admin panel at /admin.

Before anyone else can reach it

The admin panel is protected by a single shared token, not user accounts. It reads and writes API keys, so do not expose port 3000 beyond your own machine until it has real authentication. On a shared network, anyone who finds it can take your keys.

Adding course material

One markdown file per topic in seed/. The frontmatter block is required — source is what students see as the citation, so write it as a reference they would recognise. 

---
slug: sql-injection
title: SQL Injection
source: Course Notes, Week 4
category: application-security
---

Body text…
npm run seed           # adds new and changed files, skips the rest
npm run seed -- --force # wipes and rebuilds everything

Unchanged files are skipped by checksum, so re-running is cheap. Use --force only when the embedding model changed — that is the one case where the files look identical but every stored vector is stale.

Writing material that actually gets found

This is the highest-leverage thing you will do, and it is not obvious. Retrieval matches meaning, but it can only match what is written down.

  • Add an FAQ section to every topic — the real questions students ask, with answers. Student phrasing matches student phrasing, so these retrieve far better than prose.
  • Use the words students use. They say "hacking into a database", not "SQL injection". If a topic never contains their vocabulary, their question will not find it.
  • Use headings and short sections. Text is split at paragraph boundaries; structured documents split cleanly, walls of text do not.
  • Say things explicitly. A passage that depends on the paragraph before it arrives at the model alone, without that context.
  • Depth beats breadth. A topic of three bullet points becomes one weak passage and retrieves badly. A few hundred words is where this starts working.
Coverage sets the boundary

Anything not in seed/ is refused. That is the point — but it means an examinable topic missing from the folder is a topic the assistant will deny knowing.

The admin panel

At /admin, signed in with ADMIN_TOKEN from .env. From there you can add and pause API keys, choose the provider and model from a list fetched live from your key, and watch quota consumption per key.

Changes apply immediately — no restart.

The gotcha that will cost you an hour

Once a model is chosen in the panel, it overrides .env. Editing GEMINI_LLM_MODEL and restarting will appear to do nothing at all. Change it in the panel, or clear the row from the app_settings table.

Where keys live

Keys are stored in the database encrypted with ADMIN_MASTER_KEY, and only the last four characters are ever shown again. The master key stays in .env and cannot move into the database — storing it beside the ciphertext would make the encryption decorative.

Keys already in .env were imported automatically the first time the panel started. Losing ADMIN_MASTER_KEY makes every stored key unreadable; you would re-enter them, not recover them.

The limit that will actually bite you

Free-tier quota is counted per model, per day — and it is small. Google's flagship flash model allows around twenty requests a day. Not per key: per model. Lite models are far more generous, which is why answering runs on one and follow-up rewriting runs on another.

Our per-provider limits in .env are therefore an approximation. When something says "exhausted", check the model before blaming the key.

Rotation

Add keys in the panel, or comma-separate them in .env. Each becomes an independent slot with its own counters. When one is rate-limited the next serves the request and the user notices nothing. 

GEMINI_API_KEYS=key1,key2,key3

A credential that returns 429 cools until its window reopens, then returns automatically. One that returns 401 or 403 is marked dead permanently, because a wrong key will not fix itself and retrying it forever hides the one failure that needs a human.

Two rules the pool enforces: ingestion waits out a rate limit rather than leaving a half-built index, while a live question fails fast — nobody should sit through a cooldown. And an embedding pool may rotate across keys but never across models, which is rejected at startup.

Stretching a free tier honestly

  • Caching will save more than extra keys. A course bot gets the same ten questions from two hundred students. Not built yet; the single best cost decision available.
  • Small models for simple work. Already done for rewriting.
  • Rate-limit per student so one person cannot drain the pool.

Creating many accounts to multiply a free tier generally breaches provider terms, and the practical result is banned keys rather than a philosophical debate. Multiple keys across projects you legitimately own are fine.

Tuning the gate

The gate is one number: the similarity a question must reach before it is answered. It is a property of the embedding model and the corpus, not a universal constant. A value that is right today is meaningless after you change either. 

npm run calibrate

It scores every acceptance question, groups them by whether they should be answered or refused, and reports where the two groups separate. Put the gate in that gap.

Watch the margin, not just the number

The gap is currently about 0.06 — the closest must-refuse question scores 0.66, the weakest must-answer one scores 0.73, and the gate sits at 0.70. That works, but it is narrow. As you add topics, adjacent subjects will crowd it.

Re-run calibration whenever the corpus changes meaningfully. If the gap ever closes, that is your signal to add reranking — and not before.

Symptom index

Start here when something is wrong. Symptoms are what you see; causes are rarely what you would guess.

What you seeWhat it meansFix
Everything refused, scores around 0.05 The corpus was indexed with a different embedding model than the one now running. Vectors are not comparable. npm run seed -- --force. Startup now blocks on this rather than failing quietly.
all_providers_exhausted Every key is cooling, dead, or over its daily budget — usually the per-model daily cap. Switch model in the panel, add a key, or wait for the window. Check /admin for which.
404, "no longer available to new users" The model was retired for new accounts. It still appears in listings. npm run models -- --probe, then pick one that responds.
"Gemini returned an empty completion" Thinking tokens are charged against MAX_OUTPUT_TOKENS, so a small cap leaves nothing for the reply. Raise MAX_OUTPUT_TOKENS. Below roughly 500 this is likely.
Changed .env, nothing happened A model selected in the admin panel overrides the file. Change it in /admin instead.
Refuses something that IS in the material Almost always phrasing: the passage does not use the words the student used. Check the score in the reply. Add an FAQ entry using their wording, re-seed, re-calibrate.
Answers are confident but wrong Retrieval found the wrong passage, or two topics overlap near the gate. Check which source was cited. If retrieval was right, it is a prompt problem; if wrong, a content problem.
Development data vanished after tests Fixed. Tests now use a separate grounded_test database. If it recurs, check TEST_DATABASE_URL is not pointing at the main database.

How to triage in the right order

When an answer is wrong, resist rewriting the prompt. Ask first: did retrieval find the right passage? The score and the cited source are shown with every reply.

  • Wrong passage, or nothing found — a content or retrieval problem. Prompts cannot fix it.
  • Right passage, poor answer — now it is a prompt or model problem.

Most time is lost by skipping that check.

Known traps

Each of these cost real time. They are all silent — nothing crashes, nothing appears in the logs.

TrapWhy it is dangerousGuard
Mixing embedding models in one index Two models can both output 768 numbers that are entirely incomparable. Scores collapse; no error appears. Blocked at startup
Rotating an embedding pool across providers Same failure, arrived at through configuration rather than deployment. Rejected in config
Tests sharing the development database The suite truncates and re-seeds. Passing tests, destroyed data. Separate database
Changing the model without re-calibrating Thresholds do not transfer. The gate becomes arbitrary. Manual — run calibrate
Assuming a listed model works Retired models stay in listings and reject new accounts at request time. Manual — probe first
Per-provider quota limits Real limits are per model. Counters are approximate and can under-predict exhaustion. Known gap

Maintenance rhythm

Weekly
Read the refusals in the logs. Each one is either a content gap or a phrasing miss — that list is your content backlog, written by your actual students.
Content change
Re-seed, then re-run calibration and the acceptance suite.
Model change
Probe that it works, re-calibrate the gate, re-run the suite. If the embedding model changed, re-index everything.
Each term
Check the corpus still matches the syllabus. Rotate API keys. Run everything.

If you change one thing carefully, make it this

src/retrieval/gate.ts is the whole refusal guarantee. It takes candidates and thresholds and returns a decision, with no database, model or clock involved — which is why it can be tested exhaustively. Keep it that way.
